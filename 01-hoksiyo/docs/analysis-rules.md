# analysis-rules.md — 혹시요 분석 규칙

> 이 문서는 에이전트가 피드백을 **어떻게 판단하는지**를 정의한다.
> 출력 JSON의 **구조**는 `analysis-schema.md`가 정의하고, 이 문서는 **값을 채우는 기준**을 정의한다.
> 검증용 입력과 기대 결과는 `test-cases.md`를 따른다.

## 0. 문서 우선순위

기획서(`product-spec.md`) 4-2의 `확신도 높음 = 착수 가능 / 중간·낮음 = 확인 필요` 규칙은 **폐기**한다.
이후 합의에 따라 `confidence`와 `status`를 **독립적으로** 판정하며, 충돌 시 이 문서가 기획서보다 우선한다.

### 용어 매핑

이 문서는 설명 편의상 한글 라벨을 쓴다. JSON에는 `analysis-schema.md`의 값을 쓴다.

| 한글 | JSON 값 |
|---|---|
| 높음 / 중간 / 낮음 | `high` / `medium` / `low` |
| 착수 가능 / 확인 필요 | `actionable` / `needs_confirmation` |
| 요구 주체 / 전달자 | `requester` / `sender` |

## 1. 핵심 원칙

1. **모르는 내용을 추측해서 단정하지 않는다.** 판단이 어려우면 사용자에게 넘긴다.
2. **불확실한 항목을 정확히 구분하는 것이 가장 중요하다.** '높음'으로 잘못 분류하는 것이 가장 큰 오류다.
3. **원문에 없는 내용을 만들지 않는다.** 해석안은 원문에서 합리적으로 도출되는 범위로 제한한다.
4. **에이전트는 분석, 선택지, 질문까지만 한다.** 의뢰인에게 보낼 답장 작성, 전송, 견적 판단은 하지 않는다.
5. **텍스트만 처리한다.** 이미지, 시안 위 표시는 분석하지 않는다.

## 2. 처리 순서

1. 입력이 분석 대상인지 확인한다 (→ 8장 예외 처리).
2. 원문을 문장 단위로 나눈다.
3. 각 문장을 **수정 요청 / 유지 지시 / 이유·배경 / 칭찬 / 기타**로 구분한다.
4. 수정 요청을 개별 항목으로 분리하고, 근거가 된 원문 문장을 **문장 전체**로 모두 연결한다 (`original_text: string[]`).
5. 항목별 **요구 주체**(`requester`)를 구분한다 (→ 7장).
6. 항목별 `confidence`를 판정한다 (→ 4장).
7. 항목별 `status`를 판정한다 (→ 5장).
8. `needs_confirmation` 항목마다 확인 질문을 만든다 (→ 9장).
9. **누락 검증**: 모든 원문 문장이 `items[].original_text`, `validation.non_request_text`, `validation.unmatched_text` 중 하나에 있는지 확인한다.
   - 어느 항목에도 연결되지 않은 칭찬·인사·배경 문장 → `non_request_text`
   - 요청일 수 있으나 연결하지 못한 문장 → `unmatched_text` (정상 결과에서는 비어 있어야 한다)

## 3. 요청 분리 규칙

- **하나의 문장에 요청이 여럿이면 분리한다.** 접속어(`그리고`, `~하고`, `또`)로 이어진 서로 다른 수정 대상은 별개 항목이다.
- **여러 문장이 하나의 요청을 설명하면 합친다.** 요청 문장 + 이유 문장 + 배경 문장은 한 항목의 `original_text`에 함께 연결한다.
- **수정 대상이 같고 방향만 다른 표현**은 한 항목으로 두고 해석안으로 처리한다.
- **유지 지시** (`배경은 그대로`, `의상은 지금 그대로 두세요`)는 수정 항목으로 만들지 않는다. 다만 같은 항목의 해석을 좁히는 단서로 사용할 수 있다.
- **독립 문장으로 된 유지 지시**는 `non_request_text`에 넣고, 작업 시 지켜야 할 조건이므로 `notes`에 `유지 지시: <대상>`으로도 기록한다.
- **칭찬, 인사, 감사**는 항목으로 만들지 않고, 다른 항목에 연결되지 않았다면 `non_request_text`에 넣는다.
- **요청과 같은 문장에 있는 칭찬·유지 지시**는 문장을 쪼개지 않는다. 문장 전체를 요청 항목의 `original_text`에 연결하며, `non_request_text`에 중복해서 넣지 않는다.
- 문장 단위는 마침표·물음표·느낌표·줄바꿈 기준이다. 쉼표로 이어진 절은 나누지 않는다. 말줄임표(`...`, `…`)와 이모티콘은 문장 경계가 아니다. 숫자와 숫자 사이의 마침표(`1.5배`, `0.8`)는 문장 경계가 아니다.

## 4. confidence 판정 (해석의 명확성)

`confidence`는 **"이 문장을 하나의 작업으로 해석할 수 있는가"만** 본다. 작업을 시작해도 되는지는 여기서 판단하지 않는다.

| 값 | 기준 | 예시 |
|---|---|---|
| **높음** | 수정 대상과 방향이 모두 명확하고, 합리적인 해석이 하나로 좁혀진다. | "제목 폰트를 명조체로 바꿔주세요" |
| **중간** | 수정 대상은 명확하지만 **방법이나 정도가 열려 있거나**, 이전 요청을 참조하는데 이전 피드백이 없어 **내용을 대조할 수 없다**. | "저자 이름은 조금 작게" |
| **낮음** | 해석이 **여러 갈래**로 나뉘거나, 텍스트만으로 **수정 대상을 특정할 수 없다**. | "제목이 좀 묻히는 느낌이에요", "여기 이 부분이 비어 보여요" |

### 판정 시 주의

- **의심스러우면 한 단계 낮춘다.** 높음/중간이 애매하면 중간, 중간/낮음이 애매하면 낮음.
- **'조금', '좀', '느낌', '분위기', '뭔가'** 같은 정도·감각 표현은 높음으로 판정하지 않는다.
- **지시어**(`여기`, `이 부분`, `저거`)가 대상을 대신하면 낮음이다.
- **의뢰인이 문제 현상만 말하고 해결 방법을 말하지 않으면**(`묻혀요`, `쓸쓸했으면`) 낮음이다.
- 해석안이 2개 이상 떠오르는데 하나를 골라 높음으로 판정하지 않는다.

## 5. status 판정 (작업 착수 가능 여부)

`status`는 **"지금 이 항목을 확인 없이 작업해도 재작업 위험이 낮은가"**를 본다.

| 값 | 기준 |
|---|---|
| `actionable` (착수 가능) | 확인 없이 시작해도 되고, 틀려도 쉽게 되돌릴 수 있거나 결과 차이가 작다. |
| `needs_confirmation` (확인 필요) | 해석이 틀리면 수정 라운드를 다시 해야 하거나, 판단에 필요한 정보가 없다. |

### 5-1. 기본값과 경고 기준

`confidence`와 `status`는 독립이므로 자동으로 대응시키지 않는다. 다만 아래 기본값과 경고 기준을 둔다.

1. `confidence = 낮음`이면 기본값은 `needs_confirmation`이다. 낮음인데 `actionable`로 판정하려면 `confidence_reason`에 **작업자가 합리적으로 결정할 수 있는 근거**를 적어야 하며, 테스트에서 **경고 대상**으로 수동 검토한다.
2. `confidence = 높음`이면 기본값은 `actionable`이다. 단, 다음 경우에는 `needs_confirmation`으로 바꿀 수 있다.
   - 이전 피드백 또는 같은 원문의 다른 항목과 충돌하는 경우
3. `confidence = 중간`이면 다음 기준으로 판단한다.

| 중간 항목의 상황 | status |
|---|---|
| 대상은 명확하고 **정도만 열려 있으며**, 조정이 쉬운 수정 (크기, 위치, 간격 등) | `actionable` — 정도를 가정한 점을 근거에 명시한다 |
| 방법이 열려 있고 결과물이 크게 달라질 수 있는 수정 | `needs_confirmation` |
| **이전 요청을 참조**하지만 이전 피드백이 입력되지 않은 경우 | `needs_confirmation` — '이전 요청 확인 필요' 표시 |

### 5-2. confidence × status 조합

| confidence | actionable | needs_confirmation |
|---|---|---|
| 높음 | 기본 | 충돌 등 예외 |
| 중간 | 조건부 (5-1 표 참조) | 허용 |
| 낮음 | **경고 대상** (근거 필요) | 기본 |

### 5-3. 질문과의 관계

- `needs_confirmation`이면 질문을 **1개 이상** 만든다.
- `actionable`이면 질문은 `[]`이다. 중간 항목에서 **가정한 내용은 질문이 아니라 `confidence_reason`에 적는다.**

## 6. 확신도 판정 이유 (`confidence_reason`) 작성

- 한 문장으로 **왜 그 값인지** 쓴다. (예: "수정 대상과 방향이 모두 명시됨", "크기를 줄이라는 방향은 명확하나 정도가 불명확함")
- 해석안이 있으면 `confidence`가 높음이 아닌 이유와 연결해 쓴다.
- 원문에 없는 사실을 근거로 쓰지 않는다.

## 7. 요구 주체(requester) 구분

`feedback_context.sender`(전달자)와 `items[].requester`(실제 요청을 낸 주체)를 구분한다.

| 상황 | requester | requester_status |
|---|---|---|
| 제3자를 언급한 경우 (`마케팅팀에서`, `대표님이`, `팀장님이 ~하라고 해서`) | 언급된 주체 | `identified` |
| 제3자 언급 없이 전달자 본인의 의견으로 읽히고, `sender`를 알고 있음 | `sender`와 동일 | `identified` |
| 근거가 없음 | `"unknown"` | `unconfirmed` |

- 요구 주체를 밝힌 문장은 **그 항목의 `original_text`에 포함**한다.
- 요구 주체가 제3자인 것만으로 confidence를 올리거나 내리지 않는다.
- `identified`이면 `requester`는 `"unknown"`이 아니고, `unconfirmed`이면 `"unknown"`이다.
- 근거 없이 추측하지 않는다.
- `channel`과 `sender`는 프로젝트 설명 한 줄(예: `편집자 메일`)과 원문에서 근거가 있을 때만 채우고, 없으면 `unknown`이다.

## 8. 예외 입력 처리

| 입력 상황 | 처리 |
|---|---|
| 인사, 잡담, 견적·일정 문의 등 수정 피드백이 아님 | `input_type = out_of_scope`. 처리 범위 밖임을 안내하고 `items`는 빈 배열이다. 문장은 `non_request_text`에 넣는다. |
| 칭찬만 있음 | `input_type = no_revision_request`. '수정 요청 없음'으로 안내하고 `items`는 빈 배열이다. 문장은 `non_request_text`에 넣는다. |
| `다시 해주세요`처럼 맥락 없음 | 항목 1개, 낮음, 확인 필요. 구체적인 질문을 만든다. |
| `여기 이 부분`처럼 위치 지시 | 낮음, 확인 필요. 대상을 특정할 수 없으면 `interpretations`는 `[]`, `missing_information`에 위치 정보를 기록하고 "시안을 보며 짚어달라"는 질문을 만든다. |
| 수정 요청과 범위 밖 문장(견적 문의 등)이 섞임 | `input_type = revision_feedback`. 범위 밖 문장은 `non_request_text`에 넣고 답하지 않는다. |
| 이전 피드백을 참조하지만 입력 없음 | `prior_feedback_reference = not_provided`. '이전 요청 확인 필요'로 표시하고 `missing_information`에 기록한다. |
| 이전 피드백이 함께 입력됨 | 현재 요청과 대조해 `matched` 또는 `not_found`로 표시하고, 동일/상충 여부를 근거에 쓴다. |
| 이미지 첨부 | 이미지는 분석하지 않고 텍스트만 처리한다. `notes`에 기록한다. |
| 계약 범위 초과 여부 | 판단하지 않는다. |

- 값을 알 수 없는 필드는 추측하지 않고 **빈 배열 또는 `unknown`**으로 둔다. 필드를 생략하거나 `null`로 두지 않는다.

## 9. 확인 질문 생성 규칙

1. `needs_confirmation` 항목마다 **최소 1개** 질문을 만든다. `actionable` 항목은 `[]`이다.
2. **열린 질문보다 선택지가 있는 질문**을 우선한다.
   - 좋은 예: "제목이 묻히는 이유가 크기 때문인가요, 배경과의 대비 때문인가요?"
   - 피할 예: "제목을 어떻게 바꿀까요?"
3. 선택지는 해석안에서 가져온다. 해석안은 **2~4개**로 제한한다. 수정 대상을 특정할 수 없어 해석안을 만들 수 없으면 `interpretations`를 `[]`로 두고 `missing_information`에 필요한 정보를 적는다.
4. 질문은 **의뢰인에게 그대로 보내거나 조금만 고쳐 쓸 수 있는** 존댓말 문장으로 쓴다.
5. 한 질문에 하나만 묻는다.
6. 이미 원문에 답이 있는 내용을 다시 묻지 않는다.
7. 질문은 해당 항목의 `questions`에 넣는다.

## 10. 하지 말 것

- 낮음 항목을 해석 하나로 단정해 작업 목록에 넣지 않는다.
- 원문에 없는 수정 사항을 추가하지 않는다 (`전체적으로 더 개선` 등).
- 원문에 없는 수치, 색상 값, 구체적 방법을 `request`에 만들어 넣지 않는다.
- 의뢰인에게 보낼 답장 초안, 사과문, 견적 안내를 작성하지 않는다.
- 이미지 내용을 추측하지 않는다.
- 어떤 항목에도 연결되지 않은 원문 문장을 조용히 버리지 않는다.

## 11. 확정된 사항

아래는 논의를 거쳐 확정한 내용이다. 변경하려면 이 문서와 `analysis-schema.md` 5장을 함께 고친다.

- [x] 중간 + 정도만 열림 + 조정이 쉬움 → `actionable` (5-1)
- [x] 중간 + 이전 요청 참조 + 기록 없음 → `needs_confirmation` (5-1)
- [x] 낮음 + `actionable`은 금지가 아니라 **경고 대상** (5-1)
- [x] 전달자 본인 의견이면 `requester = sender`, `identified` (7장)
- [x] 해석안은 2~4개로 제한 (9장)
- [x] `input_type`, `non_request_text` 신설 (`analysis-schema.md`)
- [x] `actionable` 항목의 `questions`는 항상 `[]`, 가정은 `confidence_reason`에 기록 (5-3)

### 향후 확장 후보

- 중간 + `actionable` 항목에 선택 질문 0~1개 허용 (기획서 4-3 반영). 테스트 결과를 보고 판단한다.
