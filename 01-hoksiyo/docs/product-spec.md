**한 문장 설명**  : 프리랜서 일러스트레이터가 받은 수정 피드백을 실행 가능한 작업 목록으로 바꾸고, 의도가 불분명한 항목은 "혹시 이런 뜻인가요?" 하고 되물을 질문까지 만들어 주는 에이전트

## 섹션 1. 클라이언트 이해

### 1-1. 클라이언트는 누구인가요?

**서윤(가상 클라이언트), 프리랜서 일러스트레이터**

- 단행본 표지와 책 속 삽화(에세이, 동화, 실용서 등)를 작업한다.
- 혼자 일하며 의뢰 접수부터 납품, 정산까지 모든 과정을 직접 처리한다.
- 동시에 진행하는 프로젝트는 평균 3~4개다.
- 의뢰인은 출판사 편집자, 독립출판 작가, 자비출판 저자 등 다양하다.

※ 친구를 모델로 한 가상 인물이며, 실제 인터뷰 전까지는 본인의 프리랜서 경험을 바탕으로 세운 가설이다.

### 1-2. 클라이언트의 하루는 어떤가요?

- **오전:** 메일과 메신저(카카오톡, DM)를 확인하고 수정 피드백을 파악한다.
- **오후~저녁:** 프로젝트별로 러프, 채색, 수정 작업을 번갈아 진행한다.
- **수시로:** 진행 상황을 공유하고 새로운 문의에 답한다.

가장 많은 시간을 쓰는 일은 실제 그림 작업이지만, **가장 정신적으로 소모되는 일은 수정 피드백을 해석하는 과정**이다.

## 섹션 2. 업무 이해

### 2-1. 에이전트가 대신할 업무는 무엇인가요?

여러 프로젝트에서 받은 수정 피드백을 분석해 다음 세 가지 결과물로 정리한다.

1. 바로 실행할 수 있는 작업 목록
2. 의도가 불분명해 확인이 필요한 항목
3. 의뢰인에게 물어볼 확인 질문

### 2-2. 업무 빈도와 소요 시간

| 항목 | 내용 |
|---|---|
| 업무 빈도 | 주 3~6회 |
| 피드백 1건당 소요 시간 | 약 20~40분 |
| 주간 총 소요 시간 | 약 2~3시간 |
| 추가 대기 시간 | 의뢰인에게 질문한 후 답변을 기다리는 시간 |

※ 모두 현재 단계에서 설정한 가정값이다.

### 2-3. 현재 업무 처리 방식

서윤은 다음과 같은 순서로 수정 피드백을 처리한다.

1. 메일, 카카오톡, DM 등 여러 채널에서 피드백을 확인한다.
2. 의뢰인이 무엇을 바꾸기를 원하는지 해석한다.
3. 이전 피드백이나 기존 합의 사항과 충돌하지 않는지 기억에 의존해 확인한다.
4. 메모장이나 노션에 수정 사항을 정리한다.
5. 애매한 부분을 되물을지, 자신의 판단으로 진행할지 고민한다.
6. 되묻기로 결정하면 질문을 작성해 의뢰인에게 보내고 답변을 기다린다.
7. 확인된 내용을 바탕으로 실제 작업을 시작한다.

### 2-4. 가장 번거로운 단계는 어디인가요?

**① 피드백 해석과 ② 확인 여부 판단**

- "쓸쓸한 느낌이 더 났으면 좋겠어요."처럼 여러 방향으로 해석할 수 있는 표현을 구체적인 작업으로 바꾸기 어렵다.
- 의뢰인에게 질문하는 것이 부담스럽다. 귀찮게 느낄까 봐, 전문성이 부족해 보일까 봐 망설이게 된다.
- 결국 자신의 판단으로 진행했다가 의뢰인의 의도와 달라 수정 라운드를 통째로 다시 진행하는 경우가 생긴다.
- 이전 피드백을 기억에 의존해 확인하다 보니 기존 요청을 놓치거나 중복 작업을 하는 경우도 있다.

### 2-5. 현재 사용하는 도구는 무엇인가요?

- **메모장, 노션, 구글 문서:** 수정 사항을 직접 기록하고 정리한다.
- **범용 챗봇:** 피드백을 붙여넣어 정리를 요청하기도 한다.

하지만 기존 도구에는 다음과 같은 한계가 있다.

1. 매번 새로운 프롬프트를 작성해야 한다.
2. 불확실한 해석도 자신 있게 단정하는 경우가 있다.
3. 확신도가 낮은 항목을 별도로 분류하는 일관된 기준이 없다.
4. 모호한 피드백을 구체적인 확인 질문으로 바꾸는 기능이 부족하다.
5. 결과를 다시 검토하고 정리해야 하므로 기대만큼 시간이 절약되지 않는다.

### 2-6. 왜 이 업무를 선택했나요?

- 매주 3~6회 반복되는 업무로, 프로젝트가 늘어날수록 부담도 커진다.
- 피드백을 잘못 해석하면 재작업이라는 직접적인 비용이 발생한다.
- 입력(피드백 원문)과 출력(작업 목록, 확인 질문)이 명확해 결과를 검증하기 쉽다.
- 의뢰 문의 응대도 스트레스가 큰 업무지만, 좋은 답변의 기준을 정하기 어려워 이번 프로젝트에서는 제외했다.

## 섹션 3. 완성된 모습

### 3-1. 클라이언트가 에이전트를 사용하는 장면

**월요일 오전 10시.**

서윤은 주말 사이 도착한 수정 피드백을 메일과 카카오톡에서 복사해 에이전트 채팅창에 붙여넣는다.

프로젝트 정보도 한 줄로 입력한다.

> 《밤의 정원》 표지, 편집자 메일

에이전트는 입력된 내용을 분석해 다음 세 가지 결과를 제공한다.

- 바로 착수할 수 있는 작업 목록
- 의도가 불분명해 확인이 필요한 항목
- 의뢰인에게 전달할 확인 질문 목록

서윤은 결과를 검토한 뒤 질문을 직접 다듬어 의뢰인에게 보낸다. 답변을 기다리는 동안 확실한 항목부터 작업을 시작한다.

### 3-2. 비포 & 애프터

| 구분 | 기존 방식(Before) | 에이전트 사용 후(After) |
|---|---|---|
| 피드백 확인 | 여러 채널을 오가며 직접 확인 | 원문을 한곳에 붙여넣기 |
| 내용 해석 | 머릿속으로 의미를 추측 | 항목별 해석안과 확신도 확인 |
| 수정 사항 정리 | 직접 메모장이나 노션에 기록 | 작업 목록 자동 생성 |
| 모호한 부분 | 되물을지 감으로 진행할지 고민 | 확인 필요 항목과 질문 자동 생성 |
| 예상 소요 시간 | 건당 20~40분 | 건당 5~10분 |

※ 예상 시간은 검증 전 가정값이다.

### 3-3. 입력 예시

**예시 1. 출판사 편집자의 이메일**

프로젝트: 《밤의 정원》 표지

> 표지 전체 분위기는 좋은데, 제목이 좀 묻히는 느낌이에요. 마케팅팀에서 좀 더 눈에 띄었으면 한다고 해서요. 그리고 저번에 말씀드린 대로 저자 이름은 조금 작게 가면 좋겠습니다.

**예시 2. 독립출판 작가의 카카오톡**

프로젝트: 《할머니의 여름》 삽화

> 주인공이 너무 어른스러워 보여요. 그리고 3장 삽화는 뭔가 쓸쓸한 느낌이 더 났으면 좋겠어요. 여기 이 부분은 좀 비어 보이는데...

### 3-4. 결과물 예시

#### 예시 1. 《밤의 정원》 표지

**① 착수 가능 작업 목록**

| 수정 항목 | 확신도 | 판단 근거 |
|---|---|---|
| 저자 이름 크기 축소 | 높음 | 크기를 줄이라는 수정 방향이 명확함 |

**② 확인 필요 항목**

| 수정 항목 | 확신도 | 가능한 해석 및 판단 근거 |
|---|---|---|
| 제목이 묻히는 느낌 | 낮음 | 제목 크기 확대, 배경과의 대비 강화, 위치 변경, 배경 요소 단순화 등 여러 방향으로 해석 가능 |
| 저번에 말씀드린 요청 | 중간 | 이전 피드백과 같은 내용인지 확인 필요. 현재 이전 피드백 기록은 없음 |

**③ 확인 질문 목록**

1. 제목이 묻히는 이유가 크기 때문인가요, 아니면 배경과의 대비 때문인가요?
2. 마케팅팀에서 참고한 다른 표지나 원하는 디자인 방향이 있을까요?
3. 저자 이름 축소는 지난번에 요청하셨던 내용과 동일한가요?


> ⚠️ **변경됨:** 이 예시는 현재 기준과 다르다. 원문의 "저번에 말씀드린 대로 저자 이름은 조금 작게"는 **하나의 요청**이며, '조금'이라는 정도 표현과 이전 요청 참조 때문에 **중간 + 확인 필요**다. 현재 기대 결과는 `test-cases.md` T01과 `analysis-schema.md` 4.1 예시를 따른다.

#### 예시 2. 《할머니의 여름》 삽화

**① 착수 가능 작업 목록**

- 없음

**② 확인 필요 항목**

| 수정 항목 | 확신도 | 가능한 해석 및 판단 근거 |
|---|---|---|
| 주인공이 너무 어른스러워 보임 | 낮음 | 얼굴 비율, 표정, 의상, 체형 등 여러 요소 중 무엇을 의미하는지 불분명함 |
| 쓸쓸한 느낌이 더 필요함 | 낮음 | 색감, 인물의 포즈, 배경 요소 등 다양한 방법으로 표현할 수 있음 |
| 여기 이 부분이 비어 보임 | 낮음 | 구체적인 위치를 텍스트만으로 파악할 수 없음. 시안을 보며 확인 필요 |

**③ 확인 질문 목록**

2. 쓸쓸한 분위기는 색감을 차분하게 바꾸는 방향인가요, 아니면 인물의 포즈나 배경을 조정하는 방향인가요?
3. 비어 보인다고 말씀하신 부분이 어느 위치인지 시안을 보며 짚어주실 수 있을까요?

## 섹션 4. 거꾸로 설계하기

### 4-1. 전체 워크플로

**입력 → 분석 → 분류 → 질문 생성 → 결과 출력**

| 단계 | 수행 작업 | 주요 내용 |
|---|---|---|
| 1. 입력 | 피드백 수집 | 프로젝트 설명 한 줄, 피드백 원문 입력. 지난 피드백은 선택 사항 |
| 2. 출처 구분 | 요구 주체 파악 | 의뢰인 본인의 의견인지, 마케팅팀·대표 등 제3자의 요구를 전달한 것인지 구분 |
| 3. 요청 분리 | 피드백 쪼개기 | 여러 요청이 섞여 있다면 개별 항목으로 분리하고 원문 문장 연결 |
| 4. 해석 | 수정 의도 분석 | 각 항목의 수정 의도를 파악하고, 모호하면 2~4개의 해석안 제시 |
| 5. 확신도 판정 | 해석의 명확성 평가 | 항목별 확신도를 높음·중간·낮음으로 분류 |
| 6. 결과 분류 | 작업 가능 여부 결정 | 높음은 착수 가능 작업 목록, 중간·낮음은 확인 필요 항목으로 분류 |

> ⚠️ **변경됨:** 6단계는 확신도와 별개로 작업 가능 여부(`status`)를 판정한다. 기준은 `analysis-rules.md` 5장.
| 7. 질문 생성 | 확인 질문 작성 | 확인이 필요한 항목마다 선택지를 포함한 질문 생성 |
| 8. 결과 출력 | 정해진 형식으로 정리 | 작업 목록, 확인 필요 항목, 확인 질문 목록 출력 |

### 4-2. 확신도 판정 기준

| 확신도 | 판정 기준 | 처리 방식 |
|---|---|---|
| **높음** | 해석이 하나로 좁혀지고 수정 대상과 방향이 명확함 | 착수 가능 작업 목록에 포함 |
| **중간** | 수정 대상은 분명하지만 방법이나 정도가 열려 있거나, 이전 요청을 참조함 | 확인 필요 항목으로 분류 |
| **낮음** | 해석이 여러 갈래로 나뉘거나 텍스트만으로 수정 대상을 판단할 수 없음 | 확인 필요 항목으로 분류하고 가능한 해석안 제시 |

> ⚠️ **변경됨:** '판정 기준' 열은 유효하다(`analysis-rules.md` 4장에서 보완). '처리 방식' 열은 폐기되었다. 확신도와 작업 가능 여부는 독립 판정하며, 예를 들어 정도만 열린 중간 항목은 착수 가능일 수 있다.

### 4-3. 클라이언트가 확인하는 단계

- 확신도가 높은 항목은 바로 작업에 착수한다.
- 중간 확신도 항목은 서윤이 직접 판단해 되물을지, 자신의 판단으로 진행할지 선택한다.
- 낮은 확신도 항목은 가능한 해석을 확인하고 의뢰인에게 질문할 수 있도록 한다.
- 에이전트는 선택지와 질문까지만 제공한다.
- 의뢰인에게 실제로 메시지를 보내거나 문장을 다듬는 일은 서윤이 직접 한다.
- 해석이 잘못되었다고 판단하면 서윤이 결과를 직접 수정한다.

> ⚠️ **변경됨:** MVP에서는 착수 가능(`actionable`) 항목에 질문을 만들지 않고, 가정한 내용을 판정 근거에 적는다. 중간 + 착수 가능 항목에 선택 질문을 주는 방안은 향후 확장 후보다.

### 4-4. 필요한 정보와 도구

**필요한 정보**

| 구분 | 정보 | 필수 여부 |
|---|---|---|
| 프로젝트 정보 | 프로젝트 설명 한 줄 | 필수 |
| 피드백 원문 | 의뢰인이 전달한 수정 피드백 | 필수 |
| 과거 기록 | 이전 수정 피드백 | 선택 |
| 의뢰인 정보 | 편집자, 작가 등 의뢰인 유형 | 선택 |

> ⚠️ **변경됨:** MVP 입력은 프로젝트명, 피드백 원문, 전달자(선택), 전달 경로(선택: email/messenger/document), 이전 피드백(선택)이다. 전달자와 전달 경로는 입력값으로 `feedback_context`를 채우고, 입력이 없으면 `unknown`이다 (`analysis-schema.md` 3.2).


### 4-5. 최소 기능

이번 단계에서는 다음 세 가지 기능을 우선 구현한다.

1. **요청 쪼개기와 원문 연결**
   - 여러 요청이 섞인 피드백을 개별 항목으로 분리한다.
   - 각 항목에 근거가 된 원문 문장을 연결한다.

2. **확신도 판정과 결과 분류**
   - 항목별 확신도를 높음·중간·낮음으로 판정한다.
   - 높음은 착수 가능 작업, 중간·낮음은 확인 필요 항목으로 분류한다.

> ⚠️ **변경됨:** 확신도와 작업 가능 여부를 독립 판정한다 (`analysis-rules.md` 4~5장).

3. **확인 질문 생성**
   - 확인이 필요한 항목마다 구체적인 질문을 만든다.
   - 열린 질문보다는 선택지를 제공하는 질문을 우선한다.

### 4-6. 범위 관리

**이번 단계에서 구현하지 않을 기능**

- 이미지나 시안 위에 표시된 수정 피드백 분석
- 계약 범위를 초과하는 수정 요청 판단
- 의뢰인에게 보낼 답장 작성 및 자동 전송
- 의뢰 문의 응대, 견적, 정산
- 프로젝트별 피드백 저장 및 자동 대조
- 메일·카카오톡 등 외부 채널에서 피드백 자동 수집

**예외 상황 처리 원칙**

- 지난 피드백은 사용자가 필요할 때 직접 붙여넣는 방식으로만 지원한다.
- 이전 기록이 없으면 '이전 요청 확인 필요'로 표시한다.
- 이미지가 첨부되면 이미지 분석은 지원하지 않으며 텍스트만 처리한다.

## 섹션 5. 결과 검증

### 5-1. 결과를 어떻게 확인하나요?

에이전트의 결과를 검증할 수 있도록 다음 기준을 적용한다.

1. **원문 연결:** 모든 수정 항목에 근거가 된 원문 문장을 표시한다.
2. **해석 검증:** 확신도가 낮은 항목은 가능한 해석을 모두 보여 준다.
3. **누락 확인:** 어떤 항목에도 연결되지 않은 원문 문장이 있다면 별도로 표시한다.
4. **출처 확인:** 마케팅팀 요청인지, 편집자 본인의 의견인지 등 요구의 출처를 함께 표시한다.
5. **사용자 검토:** 서윤이 원문과 결과를 나란히 비교해 해석이 적절한지 판단한다.

### 5-2. 성공 기준

실제 피드백 또는 직접 작성한 가상 피드백 10건을 기준으로 테스트한다.

| 평가 항목 | 성공 기준 |
|---|---|
| 요청 누락률 | 원문의 요청이 누락된 경우 1건 이하 |
| 확신도 판정 정확성 | '높음'으로 분류했지만 실제로는 모호했던 항목 1개 이하 |
| 전체 확신도 판정 정확성 | 테스트 후 실제 항목 수에 맞춰 목표 개수 설정 |
| 질문 활용도 | 생성된 질문의 절반 이상을 그대로 보내거나 조금만 수정해 사용 가능 |
| 처리 시간 | 피드백 1건당 10분 이하 |

**가장 중요한 평가 지표는 확신도 판정의 정확성이다.**

잘못된 해석을 자신 있게 제시하는 것보다, 불확실한 항목을 정확하게 구분해 사용자에게 넘기는 것이 이 에이전트의 핵심 가치이기 때문이다.

### 5-3. 잘못된 입력 및 예외 상황 처리

| 입력 상황 | 에이전트의 처리 방식 |
|---|---|
| 수정 피드백이 아닌 인사, 잡담, 견적 문의 | 처리 범위 밖임을 안내하고 분석하지 않음 |
| 칭찬만 있는 피드백 | '수정 요청 없음'으로 안내 |
| "다시 해주세요"처럼 맥락이 없는 피드백 | 작업 목록 없이 확인 필요로 분류하고 구체적인 질문 생성 |
| "여기 이 부분"처럼 위치를 가리키는 피드백 | 텍스트만으로 판단 불가로 표시하고 시안을 보며 확인할 질문 생성 |
| 이전 피드백을 참조하지만 기록이 없는 경우 | '이전 요청 확인 필요'로 표시 |
| 이미지가 첨부된 경우 | 이미지 분석은 지원하지 않으며 텍스트만 처리 |

**핵심 원칙: 모르는 내용을 추측해서 단정하지 않고, 판단이 어려운 항목은 사용자에게 넘긴다.**

## 섹션 6. 계속 쓸 이유

### 6-1. 클라이언트가 계속 사용할 이유는 무엇인가요?

- **반복성:** 주 3~6회 발생하는 업무이므로 꾸준히 사용할 가능성이 높다.
- **시간 절약:** 피드백을 해석하고 정리하는 시간을 줄일 수 있다.
- **인지적 부담 감소:** 모호한 피드백을 어떻게 해석할지, 되물어야 할지 고민하는 부담이 줄어든다.
- **일관성:** 매번 동일한 형식으로 작업 목록, 확인 필요 항목, 질문 목록을 제공한다.
- **재작업 감소:** 잘못된 해석으로 수정 라운드를 낭비하는 일을 줄일 수 있다.
- **확장 가능성:** 프로젝트별 피드백 기록과 대조하는 기능이 추가되면 사용할수록 의뢰인별 작업 맥락이 축적된다.

### 6-2. 돈을 낼 가능성이 있나요?

**예상 지불 의향: 월 1,000~3,000원 (초기 가설)**

잠재 고객은 여러 프로젝트를 동시에 진행하는 프리랜서 일러스트레이터, 디자이너, 번역가 등이다.

다만 현재 만으로는 유료 전환에 한계가 있을 수 있다.

- 범용 챗봇에서도 기본적인 피드백 정리는 무료로 가능하다.
- 현재 기능은 피드백 기록을 저장하거나 이전 프로젝트와 자동으로 대조하지 않는다.
- 따라서 현재 단계에서는 사용자의 시간을 절약하는 편의 기능에 가깝다.

**향후 유료화 가능성이 높은 기능은 프로젝트별 피드백 기록 축적과 자동 대조다.**

이 기능이 추가되면 과거 합의 사항을 기억하고, 새로운 수정 요청과 비교하며, 의뢰인별 작업 맥락을 지속적으로 관리할 수 있다. 범용 챗봇과 차별화되는 지점도 여기서 만들어질 것으로 예상한다.

① 착수 가능 작업 목록에 넣고, "정도는 불명확"이라고 메모만 붙인다.

①은 빠르게 작업을 시작할 수 있다는 장점이 있지만, 작업자가 정도를 감으로 판단하다가 재작업이 발생할 수 있습니다. 반면 ②는 안전하지만 의뢰인에게 확인해야 할 질문이 많아질 수 있습니다.
